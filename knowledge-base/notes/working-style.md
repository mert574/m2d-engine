# Working style

How work is done on this repository, by agents and with the owner.

- **Parallel agents.** Many agents may work on the repository at once, each in its own git worktree.
  - Every message from the owner is a new checkpoint. After each one, use a new random port for any server or browser, and a new randomly named temp directory if you need one at all. Don't check whether the old one is still free; just switch. Carry nothing across: never write a port or a path down to use after the next message, and never read from an earlier message's temp dir.
  - Never touch, check or read another agent's work: their servers, Chrome debugging ports, worktrees, temp files, screenshots or logs. Run tests only against servers and browsers you started yourself.
  - Your own worktree's path may change between messages, though never while you are working. That needs no verification; carry on in the current one.
  - Never touch the base checkout.
- **Real GPU browser.** When running under WSL, use the native Windows Chrome (`chrome.exe`), not WSL's Chromium, which renders WebGPU in software or not at all. `launchGpuChrome` (`packages/editor-host/src/chrome.ts`) handles this; it needs mirrored networking in `.wslconfig`. Use the GPU browser for screenshots, the editor test harness and anything 3D.
- **Wait for background work before ending a turn.** A build, compile or probe you started finishes, and you report its result, before the turn ends; a turn that ends on a running job hands the owner something half-built. (16 Nov 2026: a model compile matrix was still running when a turn ended, and the owner opened a comparison page whose files were not all there.)
- **No symlinks in a worktree.** The owner's harness does not handle them well. Point at the real file, or write one.
- **The machine is shared: take a slice of it, never the whole.** Cap an asset build or a test run at a few cores (`--jobs`, `M2D_ENCODE_THREADS`) and leave the rest for the other agents and the owner. Read `/proc/loadavg` to size the slice, never another agent's processes: their process list, their kernel messages and their logs are their work, as much as their worktrees are. (16 Nov 2026: a build took every core, the machine ran out of memory and other sessions lost processes.)
- **One model build at a time, and `vite.config.js` starts one per dev server.** Editing `examples/vite.config.js` restarts every dev server running on the worktree, another session's included, and each re-runs the asset build at start; a model build holds gigabytes per compile. Before editing it or starting `buildModels.mjs`, check `pgrep -af "vite|buildModels"`. (16 Nov 2026: one config edit set three builds of the same models running at once; the machine ran out of memory, the kernel killed other sessions' processes, and another session's dev server stopped serving.)
- **MCP is first-class.** Every editor feature ships with its MCP tool or field in the same change, with a test. Agents build and check games through MCP, so a feature they can't reach is half done. See [[editor]].
- **Commits**: one per completed project phase, not per step.
- **Review your own change with probes, not a re-read.** Reading a diff finds style; it does not find a silent fallback, a missing `super`, an id scheme that breaks at the size of a shipped scene, or a test still guarding the source of truth a conversion replaced. Run the new path against the shipped data, make each new refusal fail on purpose, and grep the seams the change opened. (13 Nov 2026: an outside review of the phase 3 conversions found twelve such things that a self-review had just read past.)
- **Session summary at completion.** When a piece of work reaches completion — including a checkpoint that hands the work back part-done — summarise the whole conversation in at most four sentences — a ceiling, not a target: one or two impact-level sentences ("fixed the bugs the x change left on the examples; the showcase gained the y cvar") usually cover a session, and length follows how much the session leaves behind — high level and outcome-focused: what the session leaves behind ("worked on the first three phases of X: shipped A, B and C"), not how it went. It is not a work log — process steps (a review pass, a fix-and-retest loop) earn a mention only through what they changed, and most individual points none at all.
  - The summary is a paragraph of its own and holds nothing else: questions, offers and next steps ("commit this?", "then phase 4") go outside it, before it, and never count toward it. (Once, a question about committing was folded into the summary's paragraph, making it five sentences and only partly a summary.)
  - The boundary is the conversation, not the request. A finished request is the trigger, not the scope: the summary after the fourth request in a conversation covers all four. One conversation that ran phase 0 to phase 3 summarises phase 0 to phase 3.
  - Include nothing from before the conversation's first message, even when it continues earlier work: a conversation that opens by resuming at phase 3 summarises from phase 3.
  - Per-message resets do not start a session: a new checkpoint (fresh port and temp dir, a new scratchpad path) happens inside one. Only the conversation's first message does. When it is unclear where the conversation began, say so rather than guess. (Once, summaries covered only the latest request in a conversation that had run since phase 0; corrected to the whole conversation, the next one swung into a bulleted work log.)
- **Plain names.** Call plan items by what they are ("2D particles"), never by internal codes such as F4 or E7b.
- **Where things live.** The roadmap (`docs/contributing/roadmap.md`) is one line per big item. A big item's plan, backlog and record are a project in this knowledge base ([[editor]], [[networking]], [[3d]]). Shipped behaviour is documented on its `docs/` page. Learnings and decisions go here, as described in [[README]].
