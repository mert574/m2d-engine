# Types

Goal: the whole monorepo is TypeScript under the shared strict config, with no explicit or implicit `any`, and no package describes the engine to itself. Roadmap line: "Types".

## Where it starts (measured 20 Nov 2026)

| Workspace | JS files | JS lines | State |
| --- | --- | --- | --- |
| `packages/engine` src | 186 | 43,800 | JSDoc, unchecked; published from `src/` |
| `packages/engine` test | 108 | ~29,000 | JS; `test/helpers/*` is exported and used by kit, server and editor tests |
| `packages/server` | 23 | 1,900 | JS, published from `src/`, no tsconfig |

| `docs` | 19 | 1,750 | demos and VitePress theme, JS |

`checkJs` on the engine reports 5,913 errors: 2,407 implicit-any parameters (TS7006), 1,189 unknown properties (TS2339), ~900 nullability. 804 of them are the vendored Emscripten `basis_transcoder.js`, which is not ours to convert.

## Decisions

- **Convert, don't `checkJs`.** The engine's source becomes `.ts`, as the kit's did: erasable syntax only (no enums, namespaces, parameter properties, decorators), relative imports say `.ts`, the build rewrites them (`rewriteRelativeImportExtensions`). Every other package is TypeScript already, and JSDoc that spells out 44k lines of types is more text than the types themselves.
- **Strictness is never relaxed to make a file compile.** No package turns off `strict`, `noImplicitAny` or `noUncheckedIndexedAccess`, even temporarily: relaxing a flag and re-enabling it later is a second migration. The gradual path is the file extension instead: an unconverted `.js` file stays unchecked (`allowJs`, `checkJs: false`), and a converted `.ts` file is fully strict from its first commit.
- **Explicit `any` is the only allowed debt, and it is counted.** During the migration a converted file may write `any` where its dependency is still JavaScript or the type is genuinely hard; nothing else (`@ts-ignore`, `@ts-expect-error`, `@ts-nocheck`) is allowed at any point. A ratchet holds the count per package in a committed baseline that may only go down; it reaches zero in the last phase and the rule becomes a plain error.
- **The linter is oxlint**, for `typescript/no-explicit-any` and `ban-ts-comment`. TypeScript 7 (the native compiler the repo is on) has no JS API, so typescript-eslint cannot run against it; oxlint parses TypeScript itself and needs none. It is pinned at 1.66.0: from 1.67 it declares an optional peer (`vite-plus`) that conflicts with Vitest 5.0.5, so unpin it with the next Vitest upgrade. It sees TypeScript only: an `any` a JavaScript module's declarations get from its JSDoc is not counted, and goes when that module converts.
- **This is a major release; breaking changes are accepted** (owner, 20 Nov 2026). The engine ships as `m2d-engine@2.0.0`, the server and kit take matching majors and peer on `^2`. Nothing is kept for compatibility: no old import paths, no deprecated aliases, no shims. Where the old shape and the best practice differ, the best practice wins.
- **The public API is a set of named entry points, not the file tree.** The `"./*": "./src/*"` wildcard goes, and with it every import of an internal file by path (`m2d-engine/core/renderers/geometry/color.ts`). `exports` lists extensionless subpaths, each with `types` and `default`: `m2d-engine` (the game, scenes, entities, constraints, schema, math), plus `/schema`, `/physics`, `/actors`, `/constraints`, `/ui`, `/renderers`, `/net`, `/nav`, `/quality` and `/testing`. Each entry is an explicit `index.ts` of named exports, with `"sideEffects": false`. What a consumer imports today but no entry exports is a decision in phase 0: export it on purpose or move the consumer off it. Anything not exported is internal and free to change.
- **The engine publishes like the kit**: compiled `dist/` with declarations, built on `prepare`; `test/entries.test.ts` asserts every entry loads in plain Node from `dist` with a declaration beside it. Inside the repo a custom `m2d-source` condition on each entry points at the source, and everything asks for it: TypeScript (`customConditions`), every Vite and Vitest config (`scripts/workspaceResolve.ts`), the editor host (`engineAlias()`, read from the exports maps) and plain Node under `npm run` (`node-options` in the root `.npmrc`). The kit's entries carry the condition too, which retired the examples', docs' and editor host's kit aliases.
- **Consumers check against declarations, not the engine's source** (proven in phase 0 on TypeScript 7). A package that compiles the engine's `.ts` under its own config inherits the engine's errors and its `lib` (the kit has no DOM, the engine needs it — the kit's build hit exactly that). Each TypeScript package references `../engine/tsconfig.build.json` (`composite`) and checks with `tsc -b`, which builds the declarations when stale and substitutes them for the source. `references` is not inherited through `extends`, so a `tsconfig.build.json` restates it. The engine's build info lives in `dist/`, so deleting `dist` cannot leave `tsc -b` believing stale output is current.
- **Class fields that a base constructor sets are `declare`d.** With `target: ES2025` a subclass field written `hp: number;` is defined as `undefined` after `super()` returns, silently wiping what the base constructor's `configure()` or `static properties` merge just set. Write `declare hp: number;` for those. This is the one way an erasable conversion changes behaviour, so every phase reruns `determinism.test.js` and the GPU conformance suite.
- **Types are derived from the data, not restated.** `schema.ts` descriptors, `static params` and `static properties` get types that infer the field types (`Infer<typeof params>`), and `getConstraint(name)` is typed by a registry map, so the kit's `ConstructorParameters` workarounds and its `as any` casts disappear as a consequence rather than as edits.
- **Vendored code keeps its form.** `basis_transcoder.js` stays JavaScript with a minimal `.d.ts` for the handful of calls the engine makes. That declaration describes third-party code, not the engine, so it is not the debt below.
- **JSDoc types go when a file converts**; its prose stays. A type left in a comment beside a real one is two descriptions again.
- **A third-party module is derived from, never described again.** `rapierShared` takes either Rapier package, whose `Collider` and `RigidBody` are nominally different (private fields) while their enums are interchangeable. It names the members it touches with `Pick<Collider, ...>` over the 2D package's own types — public members only, so the 3D package satisfies them — and only the two descriptor builders, whose chained methods return their own package's class, are small structural interfaces (measured 20 Nov 2026).
- **An in-range index asserts rather than branches.** `noUncheckedIndexedAccess` types every element read as possibly undefined, a typed array's and a tuple-under-variable-index included. In the numeric kernels the loop bounds already prove the index, so the read says so (`positions[2 * i]!`) rather than inventing a fallback that would change what malformed input does; where the shape is small and fixed, a tuple type (`Mat2D`, `Rgba`) removes the question instead. The same goes for a resource that exists exactly while the renderer is `#ready` (`gl`, the batch, the passes). See the TypeScript contributing page.
- **`m2d-engine/testing` is public API.** The helpers other packages' tests use (`makeTestGame`, `RecordingRenderer`, the input and environment helpers, the physics setup) moved from `test/helpers/` to `src/testing/` and ship in `dist`, with `vitest` and `@napi-rs/canvas` as optional peers. The engine's own helpers (pixels, the GPU environment, its cast) stay in `test/helpers/`.
- **WebGPU's flag globals are missing from TypeScript 7's DOM lib.** It has the interfaces (`GPUDevice`, `GPUTexture`) but not `GPUBufferUsage`, `GPUShaderStage`, `GPUTextureUsage` or `GPUMapMode`, which the renderer uses about 140 times; `@webgpu/types` cannot fill the gap, because it redeclares what the DOM lib has (hundreds of duplicate-identifier errors). Phase 4 declares the four namespaces from the spec — a platform declaration, like the vendored transcoder's, not a description of the engine.

## The debt this deleted

Written down so it was deleted rather than inherited (owner, 18 Nov 2026): `packages/editor-core/src/engine.d.ts` and `packages/editor/src/ambient.d.ts`, the hand-written descriptions of the engine, went in phase 0 rather than phases 3 and 4. Re-keyed to the new entries they would have shadowed each entry whole — an ambient `declare module 'm2d-engine'` hides every real export it does not restate, in every package that compiles the editor core's source — so keeping them meant growing them. The editor packages check against the engine's declarations instead, and the JSDoc they proved wrong was fixed in the engine. editor-host's own stand-ins for the module it loads through Vite (`Engine`, `HeadlessGame`) became `typeof import('m2d-engine')` and `M2D`.

The project is done when no package describes the engine to itself (true since phase 0) and the `any` baseline is empty.

## Plan

One commit per phase. Every phase ends with `npm test` green (typecheck, lint, the ratchet, node and gpu suites), the determinism test bit-identical, and the examples' and docs' builds passing; the ratchet's baseline is lowered in the same commit (`--update`).

**The order is the engine's runtime import graph, leaves first** (re-derived from the code after phase 0, 20 Nov 2026). That graph has no cycles, and with the phases below no module imports one that converts after it, so a converted file never waits on a later phase for anything it runs. What does point forward is type references — every layer names `M2D` or `Scene` in its JSDoc — and those are harmless: a `.ts` file imports the type from the JavaScript module's declarations and gets sharper when phase 10 lands. So no phase's *done when* may depend on `M2D`'s or `Scene`'s types; those criteria belong to phase 10.

The scene and the game sit at the top of the graph, not the middle: `m2d.js` imports input, UI, nav, networking and the renderer registry, and `scene.js` the renderers' geometry. They convert last.

A module converting changes its importers' `.js` specifier to `.ts` (its entry's included), nothing else.

## Record

- Phase 0 (20 Nov 2026, in `cf64e86` with phases 2 and 3 — one wip commit for the three, a deviation from one-commit-per-phase): named entries and `dist/` for the engine at 2.0.0 (kit 0.5.0, server 0.2.0), every in-repo import and every docs sample on them; the `m2d-source` condition everywhere, the kit's aliases gone; project references proven; oxlint and the ratchet in `npm test`; `math.ts` and `schema.ts` converted (schema pulled forward from phase 1, because the editor core needed its descriptor type once the stand-ins went); both hand-written engine descriptions deleted. The declarations caught a real bug: the kit's `Player` and `TopDownPlayer` drew their constraints with `deltaTime` undefined (`packages/kit/test/drawDelta.test.js`).

- Phase 2 (20 Nov 2026, `cf64e86`): `core/physics/*` converted (5 modules, 2.5k lines), typed against Rapier's own declarations; `PhysicsBody` and `PhysicsWorld` are real union types on the `/physics` entry, and `game.physics` is one in the engine's declarations. The contract's option shapes (`BodyType`, the 2D and 3D creation specs, bounds, surfaces, ray hits, the world snapshot) are types now. `createPhysicsWorld`'s options are a discriminated union on `dimensions`, so a 2D world cannot be handed 3D gravity.
- Phase 3 (20 Nov 2026, `cf64e86`): the renderer contract and the WebGL2 backend (22 modules, 5.8k lines, including the renderer's own leaves from phase 1). `baseRenderer` now declares every draw call's options — the gap [[engine-surface]] recorded (the common options missing from each method's list) is closed, and `drawParticles`' `isScreenSpace`, `init`'s `textureFilter` and the post chain's full set (which the docs already documented) are in the type. Three bugs the types found, each fixed with the test that catches it: `drawAnimation` read a field (`anim.tileX`) that a real `SpriteSheet` animation has never had — its conformance fixture was a look-alike, now the real class, and 2 of its 5 tests fail against the old code; `Batch.setTarget` compared a numeric flip against a boolean argument, so every call re-flushed; and `EffectsPass.resize` passed a fifth argument `resizeRenderTarget` does not take.
- Phase 1 (20 Nov 2026): the 30 foundation modules converted (~4.5k lines), zero explicit `any` — still-JS dependencies are typed as small file-local structural interfaces or `unknown`, never `any`. `schema.ts` gained `Infer<typeof descriptor>`: the `s` builders are now generic over their literal inputs (still assignable to `SchemaDescriptor`, so descriptor-walking tools are untouched), presence follows `validate` (`required: true` or a `default` means present), and `dynamic`/`any` infer `unknown`. `gltf.ts` exports real model types (`Model`, `ModelGeometry`, `Material`, …); `cycleLook` returns `LookBlock`s. Two seams the composite build caught that a bare `tsc --noEmit` did not: declaration emit needs `camera.ts`'s `Point` exported (a JSDoc'd JS module names it), and the editor core checks against the new declarations — check with `tsc -b`, not `--noEmit`, before calling a conversion done. One build seam: bundlers resolve `new Worker(new URL(...))` strings literally and tsc's `rewriteRelativeImportExtensions` does not touch them, so the URL names `gltfWorker.ts` in source and the engine's build rewrites that one string in `dist` (`copyAssets.ts`). The examples' online tests (`keepOnline.test.js`) poll with fixed deadlines and flake when the machine is loaded; rerun before blaming a change.
- Phase 4 (20 Nov 2026): the WebGPU backend and the renderer registry converted (30 modules, 5.7k lines) — the 23 WGSL shader modules, `device`, `textures`, `environment`, `post`, `webgpuRenderer` and `renderers/index` — zero explicit `any`. The four flag namespaces (`GPUBufferUsage`, `GPUTextureUsage`, `GPUShaderStage`, `GPUMapMode`) and `GPUTextureDescriptor.textureBindingViewDimension` are declared from the spec in `webgpu/webgpuFlags.d.ts`, the platform declaration the plan called for. `frame3d.ts` sharpened as a consequence: `Material3D` now derives from gltf's `Material` (`Partial<Material>` plus the scene's `worldScale`/`planarFrame`), `Geometry3D` carries the optional vertex streams the uploader reads, `ParticleField.follow` and `StaticBatch`'s renderer-cached derivations (`bounds`/`centroid`/`minRadius`, each with its version) are declared where they live. The renderer's nullable init-time fields follow the WebGL backend's pattern (nullable field + `!` in ready paths); `basis.ts`'s `TranscodedTexture.mips` became `Uint8Array[] | null`, the truth after upload.
